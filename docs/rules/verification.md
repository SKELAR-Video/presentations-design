# Верифікація і валідатор

## Повна таблиця перевірок

`validateDeck(slidesApi, presentationId, plan, planPageIds)` читає фінальний дек через Slides API.

| # | ID перевірки | Що перевіряємо |
|---|---|---|
| 1 | `bounds` | Кожен елемент повністю в межах 0–1920×0–1080 Figma px |
| 2 | `autofit_none` | autofitType усіх TEXT_BOX = NONE |
| 3 | `font_inter_medium` | Шрифт Inter, bold=false у всіх textRun |
| 4 | `max_chars` | Довжина тексту кожного слоту ≤ max_chars зі `compositions.ts` |
| 5 | `skelar_badge` | Елемент-логотип присутній біля (1730, 100) ±20px |
| 6 | `kpi_numeric_values` | Слоти КАРТКА_N_ЗНАЧЕННЯ — тільки числові значення |
| 7 | `kpi_gap` | body-текст не перетинає ряд карток: gap ≥ gap_min (30px) |
| 8 | `theme_consistency` | Тема одна на весь дек (dark або red) |
| 9 | `logo_overlap` | Жоден TEXT_BOX не перетинається із зоною логотипа |
| 10 | `bento_left_overlap` | ЗАГОЛОВОК і ТЕКСТ в лівій колонці bento_right_* не перекриваються |
| 11 | `bento_trailing_period` | Текст бенто-картки не закінчується одиничною крапкою (після auto-strip) |
| 12 | `bento_layout` | pt ≥ 10pt (10pt — навмисна нижня межа, контент ніколи не скорочується); текст не переповнює; буліти присутні якщо є `·` |
| 13 | `kpi_row_geometry` | Ряд від PAD до PAD+UW; дно ≈ kCY+cardH |
| 14 | `content_integrity` | Кожен слот є точним підрядком вхідного ТЗ (з урахуванням виключень) |
| 15 | `fragment_coverage` | Кожен вхідний фрагмент присутній у слотах плану |
| 16 | `no_literal_asterisk` | Жоден слот не містить `*` |
| 17 | `no_duplicate_title` | ЗАГОЛОВОК не дублюється між сусідніми слайдами (виключення: variant siblings `_v1`/`_v2`) |
| 18 | `badge_item_max_chars` | Кожна мітка в ПУНКТИ ≤ 20 символів |
| 19 | `slide_count_matches_sheets` | Кількість слайдів ≥ кількість аркушів (може бути більше через variant expansion) |
| 20 | `content_coverage` | **Deck-level**: кожен рядок брифу присутній хоча б в одному слоті дека |
| 21 | `text_overflow` | Текст, реально записаний у бокс, не вищий за сам бокс (бокси з 2+ параграфів) |
| 22 | `readable_font` | Баді-текст не дрібніший за читабельну підлогу 18pt; недобір до 20% — PASS із поміткою, більший — FAIL із числами |

## `readable_font` — чому `text_overflow` її не замінює

`text_overflow` питає «чи текст лишився в межах боксу». Але бокс **завжди** влазить, якщо дозволити шрифту меншати досить далеко — тому суцільна стіна 10pt проходить цю перевірку як здорова. Саме так газетні слайди й лишались невидимими для валідатора.

`readable_font` питає те, що питає глядач: чи це можна прочитати. Вона бере **найменший** кегль, реально записаний у бокс (один великий лід-ін не робить картку читабельною, якщо список під ним на 10pt), і рахує, скільки б знадобилось при 18pt у тому самому боксі.

Звіт одразу дає варіанти рішення, а не констатацію:
```
КОЛОНКА_2: 10pt (floor 18) — at 18pt needs 1180px of 580px → split into 3 or cut 51%
```

Службові елементи (пілюля варіанта дизайну, дата, лого) виключені — вони не контент і законно дрібні.

Правило і межі → `docs/rules/typography.md`, «Читабельна підлога».

### Ті самі цифри структурою — `overloads`

Речення вище годиться для лога, але з нього не можна ні зібрати екран, ні поділити слайд. Тому перевірка звітує **двічі з одного вимірювання**: реченням і полем `overloads` у звіті — номер слайда, ім'я слоту, потрібна й наявна висота, на скільки слайдів розкладати, скільки відсотків зрізати.

Другої оцінки не існує: обидва звіти — це один і той самий замір із готового файлу. Саме тому питання людині ставиться **після** генерації, а не до неї — до неї правдивої цифри просто немає (див. `docs/rules/content-mapping.md`, виняток про розкладання).

Імена слотів беруться з карти `slotObjectIds` самого генератора. З файлу їх не відновити: на момент, коли дек існує, плейсхолдери `{{ТОКЕН}}` уже перезаписані тим самим текстом, який ми міряємо. Бокс, якого не вдалось назвати, потрапляє в речення, але не в `overloads` — пропонувати розкласти те, чого ми не знайдемо в плані, означало б давати обіцянку, якої не виконаємо.

### Свідоме рішення — не дефект

Слайд, про який людину спитали і вона обрала лишити дрібний шрифт, несе `keepSmall` у плані. Тоді:

- `readable_font` **проходить** із поміткою «лишено за рішенням людини» — вимір той самий, змінюється тільки вердикт;
- у `overloads` слайд лишається, але з `accepted: true` — рішення видно, проте воно більше не питання;
- екран показує його рядком «більше не питаю», а не серед відкритих.

Чому прохід, а не FAIL: `typography.md` каже «читабельність — стан за замовчуванням, відступ від неї — рішення людини, а не коду». Перевірка, яка після цього рішення й далі падає, сперечається з власним правилом.

`keepSmall` живе в плані, а не на сторінці, — інакше перезбирання одразу після вибору доповіло б цей вибір назад як свіжу проблему. І не переноситься на нові брифи: інший дек — інші слайди, відповідь про один нічого не каже про інший.

## `text_overflow` — чому вона знадобилась

Двічі поспіль текст фізично вилазив за межі картки (а на слайді 7 — і за нижній край слайда), і **жодна перевірка цього не бачила**: `max_chars` рахує символи, `bounds` перевіряє бокс, `bento_layout` працює з планом. Ніхто не порівнював висоту тексту з висотою боксу.

Перевірка читає готовий файл: по кожному параграфу бере його фактичний кегль і фактичний `spaceBelow`, рахує рядки і порівнює з внутрішньою висотою боксу.

**Мірка спільна з генератором** — `lib/textfit.ts` (0.5 ширини символа, 1.1 висоти рядка, порожні абзаци рахуються). Різниця тільки в запасі: генератор зупиняється на `FIT_MARGIN` (95% боксу), перевірка питає голе «чи вилазить насправді» (+8px на округлення). Тому PASS означає «обидва порахували те саме», а не «дві схожі формули випадково зійшлись». Деталі й чому саме ці числа → `docs/rules/typography.md`.

Пійманi дефекти: +132px, +77px, +57px, +157px, +243px — усі далеко за межами похибки.

Обмеження: бокси з одним параграфом (заголовки) не перевіряються — у них свої правила word-fit і фіксованої висоти.

## Нуль втрати контенту — три рубежі

Втрата контенту раніше була невидимою для Slides-брифів: `mapSlides1to1` не віддавала `sourceText`, тому verbatim-перевірка `content_integrity` тихо вимикалась на ВСІХ слайдах, а `fragment_coverage` жила лише у `validatePlan`, яку реальна генерація ніколи не викликає. Доведено на проді: видалення 622 символів з `closing` + підміна слоту вигаданим текстом давали `validation.pass=true`, 0 FAIL.

Тепер три рубежі, всі три на живому шляху:

1. **Retry** (`mapSlides1to1`) — якщо після маппінгу є рядки брифу, що не потрапили в жоден слот, LLM отримує звіт «ці рядки будуть втрачені» і один retry. Retry приймається лише якщо втрачає менше за перший прохід.
2. **Детермінований fallback** (`applyCoverageFallback` у `lib/coverage.ts`) — незалежно від рішення LLM жоден рядок не зникає. Спершу пробує власний body-слот композиції (`ПІДЗАГОЛОВОК`/`ТЕКСТ`) — `closing` лишається `closing`; тільки якщо слоту немає або текст перевищує його `max_chars` — даунґрейд у `title_body`.
3. **`content_coverage`** (`validateDeck`) — фінальна сітка по фактах дека.

Ключові рішення:
- `slide.fragments` — рядки брифу зберігаються **на самому слайді**, не за індексом. Індексний масив ламався б після `expandPlanWithVariants` (варіанти зсувають нумерацію).
- Перевірка **deck-level, не per-slide**: варіант дизайну має право структурно дропнути слот (напр. `ТЕКСТ` при переході в `two_columns`), тому per-slide давав би хибні FAIL. Питання ставиться так: «чи існує цей рядок бодай десь у деку».
- Порівняння **м'яке** (`looseNorm` у `lib/coverage.ts` — спільний для маппінгу, валідатора й тестів): NBSP, `\v`, `:`→`—`, зрізана крапка, регістр — це навмисні трансформації рендеру, не втрата.
- Порівняння йде і з **до-рендерним знімком** слотів (`plan.preRenderSlots`), щоб компакція чисел (`2 000 000`→`2M`) і де-дублювання `ПІДПИС` не читались як втрата.
- Обмеження, яке треба знати: якщо рядок брифу дублюється на двох аркушах, deck-level перевірка вважає його присутнім, поки він є хоча б на одному слайді.

## Жорстке правило: не «готово» поки FAIL

НЕ оголошувати «готово», поки `validation.pass === true`.  
Якщо хоч один FAIL — аналізуй причину, правь **сам**, без перекидання на користувача.  
Макс 2 спроби → після 2 невдач СТОП, звіт числами.

Коли все PASS — дати лінк + вивести звіт (PASS/FAIL по слайдах).

## Інтервали — перевірка з файлу

```bash
node scripts/diag-spacing.js <deckId> [номер слайда|all]
```

`inspect-deck` віддає по кожному текстовому боксу `paragraph_count` і `paragraph_facts[]` (`lineSpacing_pct`, `spaceAbove_pt`, `spaceBelow_pt`, `soft_breaks`). Без цього дефект «список читається як полотно» **невидимий**: `\v`-склеєний список і нормально розділений мають однаковий `text` і однаковий `paragraphs[]`.

Що має бути на боксі зі списком (≥2 пунктів): `lineSpacing=90%`, `spaceBelow ≠ —`, `soft_breaks(\v)=0`. Скрипт сам виводить вердикт `DIFFERENT ✅` / `SAME ❌`.

Він також виводить `all_fonts=[...]` — **усі** кеглі в боксі, не лише перший. Без цього дефект «перший пункт списку роздутий на +8pt» був невидимий: `fontSize_pt` читається з першого текст-рану, тобто саме з роздутого рядка, і бокс виглядав як однорідні 22pt. Правило → `docs/rules/bento.md`.

## Панель фактів (inspect-deck)

`buildPresentation` повертає `{ url, validation, deckFacts }`.

Факти з реального файлу (через `DeckFactReport`) відображаються на `/result` у панелі «Факти з файлу». Перевіряє fontSize, геометрію, наявність контенту — на основі того, що реально записалось у Slides.

## Fixture-валідатор

```bash
npm run validate-fixture
```

*(колишня команда `npx ts-node --skip-project …` падає на актуальному Node з `ERR_UNKNOWN_FILE_EXTENSION` — npm-скрипт компілює у `.fx-build/` і запускає звідти.)*

Набори тестів:
- **Fixture 1** — коректний badges-слайд → очікується PASS
- **Fixture 2** — asterisks, дублікат заголовка, довгий badge → очікується FAIL
- **Fixture 3** — fragmentGroups, всі фрагменти присутні → PASS
- **Fixture 4** — fragmentGroups, один фрагмент відсутній → FAIL
- **Bento height+width** — math: word-fit + height-check для bento_right_2/3
- **Bento geometry** — math: інваріант `card_bottom = 980` для 5 композицій
- **Word-break** — math: `longestWordPx × 1.1 ≤ innerW` для bento + title кроків
- **Fixture 5** — `content_coverage`: closing зберіг body-текст → PASS
- **Fixture 6** — `content_coverage`: closing втратив body-текст (той самий реальний баг) → FAIL
- **Fixture 7** — `applyCoverageFallback`: усі втрачені рядки відновлені, композиція `closing` збережена
- **Fixture 8** — спільна мірка `lib/textfit.ts` на реальних payload'ах: `three_columns` зі слайда 6 отримує `group_font ≥ 13pt` (було 11pt) і жодна картка не переповнюється; надбавка +8pt на першому рядку слайда 14 дає 497px у боксі 440px і має бути відкинута. Викликає **справжні** функції, не копію їхньої арифметики.

## Маркер-тест для верифікації деплою

Щоб переконатись що зміни коду доходять до дека, додай тимчасовий маркер:

```ts
// lib/google.ts, у replaceAllText-циклі
if (compId === 'cover' && slotName === 'ПІДЗАГОЛОВОК' && replaceText.trim()) {
  replaceText = replaceText + ' TEST-A1'
}
```

Генеруй → `TEST-A1` з'явився = код живий; не з'явився = стейл-білд або master не перебудовано.  
Видали маркер одразу після підтвердження.
- **Fixture 9** — плоскі колонки: вища площа (440 → 486 → 575px) дає більший кегль і текст усе одно влазить
- **Fixture 10** — порожній абзац (розділювач груп `\n\n`) рахується як рендерна висота: 2 порожні рядки при 18pt = 154px
